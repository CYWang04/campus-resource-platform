## 设计建议，进入 F01 评审

| 编号 | 方案/默认值 | 理由与评审重点 |
| --- | --- | --- |
| P01 | M1 管主数据与资源状态，M2 管身份权限，M3 管通知中心和审计汇总 | 不增加服务；评估 M1 工作量与各能力故障责任 |

| P03 | 单仓、一个 MySQL 实例、三数据库与独立账号；固定服务名+HTTP、Compose | 简化课程规模运维，维持数据所有权 |
| P04 | 身份使用 8 小时随机会话令牌，服务端保存摘要，前端仅内存保存，刷新后重新登录；M1/M3 向 M2 校验 | 实现简单、注销和角色变更及时生效；评估额外身份调用与使用体验 |
| P05 | 外部 `/api/v1`，内部 `/internal/v1`；UUID 字符串、UTC 存储、上海时区展示、半开时间区间 | 接口详细提案见 INTERFACES |
| P06 | 待审批不预占；两级审批，院系审批人→资源管理员；禁止自审；每级 24 小时且不晚于预约开始 | 任务书只要求多级和超时；具体层级与参数是项目默认值 |
| P07 | 未来 7 天可预约；签到窗口为开始至开始后 15 分钟之前 | 日期范围、签到窗口不是任务书指定参数 |
| P08 | 维修由 M1 确认后起效，结束时间未知；取消该时刻尚未结束的当前及全部未来重叠预约/占用，结束后不恢复 | 是 U07/U08 的具体时段解释；“全部未来预约”的影响必须由团队明确认可 |
| P09 | 派单后 24 小时未开工、开工后 48 小时未完工升级；资源管理员验收且维修人员不能自验 | 时限与验收人员属于需求细化建议 |
| P10 | 普通资源停用/开放时间调整若影响有效预约则拒绝；紧急不可用通过维修流程处理 | 避免隐式取消，注销使用软停用保留历史 |
| P11 | 持久化待同步任务+幂等 HTTP；按来源版本及资源版本防乱序；M1 教室事务锁统一串行资源变更 | 针对并发、超时、重复请求和维修取消终态，见 INTERFACES |
