## 范围、约束与方案

本轮交付 M2 负责的维修取消接收端、持久化通知、迟到同步结果保护和专项测试。沿用现有两级审批、服务凭证与数据库隔离，不修改已部署迁移，不重写已有预约功能。M1 的取消事件生产、来源永久失效与可靠投递由 M1 接入；本轮不能声称完整 M1→M2 链路已经验收。

取消事件采用鉴权内部 HTTP 接口；在同一 M2 事务内校验事件、锁定申请、去重、更新终态、记录审计并保存通知任务。相比请求内同步发邮件，此方案允许通知服务故障后继续重试，且不会出现取消已落库而通知任务丢失的情况。

`CANCELLED_MAINTENANCE` 为申请终态，覆盖已批准、正在同步批准和正在同步撤销的申请；已驳回、已超时、已主动撤销和未进入资源同步的申请不改写。迟到成功或失败均不得覆盖取消终态。取消后必须新建申请，不恢复原 ID。

## 验收标准

- 无服务凭证、错误凭证和非法参数请求被拒绝。
- 已批准及资源同步中申请可取消；申请教室与来源版本不匹配时拒绝。
- 同事件重复请求只产生一次审计及通知；同事件 ID 不同内容返回 409。
- 不同取消事件不能重复通知同一申请；已有非资源终态保持不变。
- 取消后迟到的批准成功、失败及撤销成功均不能恢复或改写申请状态。
- 通知在取消事务中持久化；投递失败保留原事件标识进行重试。
- 当前业务申请、审批、撤销和权限回归检查不被破坏。

## 交给 M1 的接口约定

`POST /internal/v1/room-applications/{id}/maintenance-cancellation`，仅服务网络可访问。请求使用现有 `X-Service-Key`；`id` 为 M2 申请 UUID。

```json
{
  "eventId": "60000000-0000-0000-0000-000000000001",
  "roomId": "10000000-0000-0000-0000-000000000001",
  "sourceVersion": 1,
  "maintenanceSourceId": "50000000-0000-0000-0000-000000000001",
  "reason": "教室紧急维修"
}
```

- `eventId`：M1 事务内生成并持久化；重试使用相同 ID 和相同内容。
- `sourceVersion`：失效的 `M2_ROOM_APPLICATION` 来源版本，不能大于 M2 当前已知版本。撤销与维修交错时，允许较早的已生效来源版本取消仍在释放中的申请。
- `maintenanceSourceId`：导致失效的 M3 工单来源 ID，作为追溯证据。
- `reason`：非空，最多 500 字符，不包含凭证或个人敏感信息。

200 返回 `{data:{eventId,applicationId,state},requestId}`，表示本地事务已确认；不表示通知或邮件已送达。同事件内容冲突、教室不匹配或未知来源版本返回 409；申请不存在返回 404；无服务凭证返回 403；格式错误返回 400。发送方对网络失败、5xx 使用相同事件重试；明确 4xx 保留失败证据，核对契约后处理，不盲目更换事件 ID。

M1 尚需实现以下部分，不能仅调用本接口代替资源失效：在添加维修限制的同一事务中永久失效受影响的 M2 来源并保存投递任务；解除维修和更高版本的旧申请写入不得恢复同一来源；历史操作重放返回当前来源状态。M2 接收端不会访问 M1 数据库，也不会冒充 M1 解除资源。

前端需把 `CANCELLED_MAINTENANCE` 显示为“因维修取消”，对应操作为新建申请；本轮没有修改页面。现有 Nginx 不开放 `/internal/`，内部接口不得改为公网路由。
