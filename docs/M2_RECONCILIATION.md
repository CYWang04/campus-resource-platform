# M1/M2 维修取消整合

日期：2026-10-31。工作分支：`m2-maintenance-cancellation`。关联 PR #2、#5，任务 B02-04。

## 授权与范围

用户已明确授权本次由 Agent 解决两分支代码冲突并完成测试；这是对 AGENTS 人工冲突处理规则的本次例外，不是全组规则变更。本轮只在功能分支整合，不合并到 main，不部署，不删除数据。保留两边有效的业务逻辑与测试，统一为一个 M2 接收端和一个通知投递器。

## 方案

1. 接收端以复数 `/maintenance-cancellations` 对接 M1，同时保留原单数路径为兼容别名；两条路由使用同一状态机。M1 已有载荷不含 reason，接收端提供固定默认原因，显式空原因仍拒绝，指纹使用归一化后的内容。
2. M2 解析 M1 返回的当前来源状态，避免将历史 APPLIED 当作当前有效占用；维修取消终态覆盖批准/撤销的迟到结果，事件、审计和通知保持同事务。
3. 不改写任何一份已执行过的 V3 内容。把公共 V1/V2 与前向 V4 放在公共迁移目录，分别保留 M1、M2 原有 V3 作为可选历史路径。新环境默认 M2 路径，已经执行 M1 V3 的数据库明确选择 M1 路径；一次启动只加载一个 V3。V4 以增量方式补齐兼容表结构，保留旧事件收据与通知数据，不自动修复历史表或重建数据库。
4. 保留 M1 的资源失效、持久化投递和回归脚本。前端维持项目既有分工边界，因维修取消的中文展示继续交给前端负责人，本轮不改 web。

保留两份 V3 并简单改编号不能解决重复建表；删除某一历史也会让另一类已初始化数据库校验失败，因此采用显式历史路径加前向迁移。路径选择应依据实际 Flyway 记录，由相关组评审，不自动猜测或掩盖校验失败。

## 验收

- 保留已有取消/并发/事务回滚测试，新增历史资源结果与失败恢复的检查。
- 两条 Flyway 历史从空库及已有 V3 数据升级到 V4 均可验证，旧迁移内容不变，事件和通知不丢失。

- 最终检查不含冲突标记，不重复注册取消路由，不启动两套通知投递任务。

## 部署前选择已有迁移历史

此处的 m1/m2 指 **M2 数据库原有 V3 的来源分支**，不是切换服务数据库。M1、M3 的数据库及迁移配置维持原样。

先只读查询 M2 自己数据库的历史：

```sql
SELECT version, script, checksum, success
FROM flyway_schema_history
WHERE version = '3';
```

| M2 历史记录中的 script | M2_MIGRATION_LINEAGE |
| --- | --- |
| V3__maintenance_cancellation.sql（单数） | m1 |
| V3__maintenance_cancellations.sql（复数） | m2 |
| 空数据库或尚未执行 V3 | m2（默认） |

Docker Compose 在本地 .env 设置 M2_MIGRATION_LINEAGE=m1 或 m2；已有 .env 不会被初始化脚本覆盖，因此升级前必须核对。原生启动 M2 时设置同名环境变量。应用只加载 common 和所选历史目录，V4 自动增量补齐另一侧兼容表及通知字段。

选择后沿用该历史路径，不在 V4 成功后随意切换。若脚本名未知、存在失败记录或校验不匹配，保留现场核对实际数据库，不运行 repair、不改历史校验值、不删卷、不重建已有数据库。两份 V3 均保持原始字节；公共 V1/V2 也只搬目录，不改内容。

旧 M1 事件收据保留原值；合法重放时补齐规范收据，不重发业务通知。旧通知 application_id 按已知事件键回填，不能关联的行保留 NULL；新增 created_at 为迁移时默认值，不是伪造旧事件发生时间。
