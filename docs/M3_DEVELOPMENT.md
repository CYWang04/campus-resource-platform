## 第一批范围、方案与验收

关联 B03。先补现有工单状态、职责与事务回归测试，再修复完工命令幂等。改动限定 M3 后端、专项测试和本模块记录，不改变业务接口路径、数据库迁移或其他模块实现。

完工命令应将操作、工单 ID 和说明一起纳入指纹；相同请求重试返回当前工单，不再次写入说明、完工时间或审计。同键不同说明返回 409。旧无说明 `/complete` 路径继续兼容。不同用户的幂等键仍各自隔离。

测试从现有 SQL 构造表，用 H2 MySQL 模式运行真实 JDBC 与 Spring 事务；V2 中 MySQL 的多列 ALTER 和 AFTER 语法仅在测试夹具中转换，不修改生产迁移。覆盖正常闭环、越权、非法状态、取消、评价、重复及事务回滚。它不替代真实 MySQL/Flyway 或跨模块 HTTP 联调。当前账号无 Docker socket 权限，不修改权限，不启动或中断共享服务。

兼容边界：保留原无说明 `/complete` 接口及其指纹；带说明 `/complete-with-note` 使用包含说明的新指纹。升级前已保存的带说明命令没有请求体指纹，无法可靠验证重放内容，重用其旧键会返回 `IDEMPOTENCY_CONFLICT`，客户端应查询工单确认结果；不得自动换键重复执行。无需数据迁移。新增调用方继续使用原请求路径和字段。

## 第二批范围与验收计划

沿用现有 M2 维修人员目录 API，以当前管理员身份查询人员，M3 只保存目录返回的姓名和邮箱；原派单请求字段保留，用于请求指纹与兼容，不能作为可信人员资料。目录查询在 M3 写事务之外执行，成功重放不重复查询目录。测试覆盖伪造资料、未知人员、依赖失败、权限及重试。

超时升级拆成独立调度入口与事务服务，使用可注入时间；锁定工单后重新检查状态、24/48 小时阈值和升级等级，只有成功升级才记录通知及审计。每单独立事务，失败可在下次扫描重试。测试覆盖边界、重复、并发、已结束工单和写入失败回滚。本轮不新增接口路径、状态枚举或迁移，不修改 M1/M2。

### 第二批实现与结果

- 新增 `WorkerDirectory`，封装 M2 现有公开人员目录请求，透传当前用户 Authorization 和请求标识，连接/读取超时分别为 3/5 秒。人员不可用返回 409；目录异常或内容不完整返回 503；目录返回的 401/403 保留权限失败语义。人员资格以派单前 M2 查询结果为准。
- 新增 `WorkOrderAssignments` 编排鉴权、重放查询、远端人员核验与本地写入。姓名及邮箱使用目录结果；原请求字段继续纳入原派单指纹，同键异内容仍返回 409。已成功派单的原请求重放无需再次读取人员目录，但仍需身份鉴权。写事务内锁工单并复查命令，持久化操作、通知和审计。
- 新增 `WorkOrderEscalations` 与 `EscalationWorker`，替换原 `DeliveryWorker` 中的超时扫描。使用 UTC 时间参数查询候选；达到 24/48 小时后才升级，事务内再次校验当前工单，单次成功只写一次通知和审计。扫描每次最多处理 100 个候选，每单独立事务，数据库失败记录提示并继续其余候选，下次扫描重试。通知接收者沿用现有报修人，不宣称已增加管理员通知。
- 原实现上派单 HTTP 回归实际有 4 项失败，复现接受伪造资料、未知人员及忽略目录故障等行为，见 `.work/m3/assignment-red.log`。修复后 HTTP 测试覆盖完整目录响应、权限失败、异常载荷、资料缺失及重放。
- 反向验证：临时移除升级服务 `@Transactional`，两项写入失败回滚测试均按预期失败（升级等级实际为 1，期望为 0）；恢复源码后重新执行完整 M3 `verify`。证据为 `.work/m3/escalation-without-transaction.log`，未提交变异源码。
- 最终 `bash scripts/m3-dev.sh mvn -B -f backend/pom.xml -pl m3 -am verify` 成功：45 项测试（工单数据库 15、升级 15、派单 HTTP 13、原有职责测试 2），0 失败、0 错误、0 跳过，`git diff --check` 通过。最终日志为 `.work/m3/second-batch-final.log`。

测试中的人员目录与鉴权为本机 HTTP 测试服务器，持久化为 H2；没有运行真实 M2、MySQL/Flyway、页面或远端 CI。本轮仅有 M3 内部代码与测试变更，没有调整其他模块、公共层、接口路径或数据库结构。后续优先完善 M1 同步响应校验、任务失败可观察性与页面反馈。
