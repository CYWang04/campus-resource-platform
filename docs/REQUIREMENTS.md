历史分析保留在 [PJ任务书分析](sources/PJ任务书分析.md)。其中“尚待确认”不代表此后仍未选择；当前状态以 [DECISIONS](DECISIONS.md) 为准。

## 项目组织与范围

| 编号 | 要求 | 来源 |
| --- | --- | --- |
| R-ORG-01 | 约六人独立交付完整平台，至少三个模块组，各认领一个模块；项目组是环境与评级单位 | 第 1 页 |
| R-ORG-02 | 公共层归属由组内决定并书面记录：工作量、接口契约、故障责任、方案理由与达成一致过程 | 第 1 页 |
| R-ORG-03 | 技术栈自由，不提供脚手架；必须使用 AI 编程助手并体现规划、验收和工程过程 | 第 1～2 页 |
| R-ORG-04 | 项目组拥有开发、测试、生产环境，组内共享；三环境不等于三台物理机器 | 第 1 页 |

早期材料明确使用 CodeArts、每组两台华为云服务器，新任务书未重述不等于撤销。用户计划通过 GitHub 分享本仓库，需要核对二者配合，不能自行声称平台要求已变更。

## M1：自习座位预约

| 编号 | 最终需完成的能力 | 来源 |
| --- | --- | --- |
| R-M1-01 | 管理教室/座位登记、注销、可用性、唯一座位编号与开放时间 | 第 5 页 |
| R-M1-02 | 院系自习室仅向本院系开放；角色与权限可管理、新角色可配置 | 第 5 页 |
| R-M1-03 | 条件查询、整点小时预约，单次默认最多 4 小时且可配置 | 第 5～6 页 |
| R-M1-04 | 教室屏幕每日动态、与教室关联的编码/二维码；Web 输码或小程序扫码签到 | 第 6 页 |
| R-M1-05 | 开始前 15 分钟提醒；开始后 10 分钟未签到再次提醒 | 第 6 页 |
| R-M1-06 | 开始后 15 分钟仍未签到则取消、释放、通知并记一次违约 | 第 6 页 |
| R-M1-07 | 预约历史及再次预约同一座位；再次预约需按当前状态校验 | 第 6 页；后半为实施解释 |
| R-M1-08 | 运营预约统计；固定/移动导轨插座标记及筛选 | 第 6 页 |

学生端可选 Web 或小程序，本设计采用 Web。通知需真实推送，单纯控制台打印或写数据库不能作为完整提醒验收。7 天预约范围、具体签到窗口等为项目默认提案，不是任务书参数。

| 编号 | 最终能力 | 来源 |
| --- | --- | --- |
| R-M2-01 | 整教室申请资格、多级审批、通过、驳回、超时自动撤销；需求由小组细化 | 第 1 页 |
| R-M3-01 | 故障上报、派单、维修中、超时升级、完工验收、评价；需求由小组细化 | 第 1 页 |

| R-INT-02 | 任务书示例：M2 通过按时段占全室座位；驳回/超时撤销回滚；M3 维修中下架、验收通过恢复 | 第 1～2 页 |

两条链路在任务书中以“集成示例”给出，本项目设计拟采用为基线；不能误写成所有接口都是教师逐项指定。期末真实跨模块网络调用和状态写回是明确演示要求。

用户已选择审批不抢占、维修取消个人预约和已批准申请。多级审批具体层数、工单时限和维修开放结束时段仍是待评审细节，见 DECISIONS。

## 工程过程与证据

| 编号 | 要求及需保留的证据 | 来源 |
| --- | --- | --- |
| R-ENG-01 | 机器可读项目规则受版本管理；AI 任务有范围、约束、验收，先方案再实现 | 第 2 页 |
| R-ENG-02 | 从首个提交保存规则、需求、决策、代码、迁移和流水线；Git 为主要过程证据，聊天不能替代 | 第 2 页 |
| R-ENG-03 | AI 变更经人工验收后提交，小范围可评审；提交关联任务并说明理由 | 第 2 页 |
| R-ENG-04 | 分支策略与 MR 评审；冲突由人处理，不能由 AI 自行合并冲突 | 第 2 页 |
| R-ENG-05 | 提交/MR 触发构建测试；失败阻断后续阶段，测试不通过不能合并 | 第 2～3 页 |
| R-ENG-06 | 测试环境无人为审批地自动部署，一次覆盖整组模块；生产人工审批、可回滚、当前版本可查 | 第 3 页 |
| R-ENG-07 | 跨模块、公共层和 schema 变更组内评审；部署窗口或互斥机制避免干扰集成测试 | 第 3 页 |
| R-ENG-08 | 迁移版本化、可重复执行、空库可重放，不手工改库；种子幂等且与业务数据分离 | 第 3 页 |
| R-ENG-09 | 需求基线关联实现和验证，未完项保留；测试验证真实行为，故意破坏实现应使测试失败 | 第 3 页 |
| R-ENG-10 | 基础设施尽量脚本化，Docker 为建议；比较架构候选而非直接接受 AI 第一个方案 | 第 3 页 |
| R-ETH-01 | 伦理融入开发各阶段，每位成员在个人论文结合真实工作讨论问题、措施和不确定性 | 第 3 页 |

早期课程文件中“伦理强烈建议”的表述已被新任务书的明确要求补充。论文格式、独立伦理章节和截止仍未明确。应保存权限公平、数据访问、误处罚、维修影响、AI 验收责任等真实决策和验证，不能虚构事件。

## Review 与最终展示

| 节点 | 内容 |
| --- | --- |
| 启动 | 分组、认领、分工、公共层归属决策 |
| Review 1 | 需求基线、任务依赖、架构与首轮功能、规则/AI 协作、风险 |
| Review 2 | 主功能、集成、测试通过、迁移进流水线、提交到部署演示、质量保证 |
| 期末 | 完整业务及人机协作、工程过程的真实演示 |

期末必须实际演示（第 5 页）：

1. 全新环境通过流水线部署。
2. 一次提交自动触发构建和测试。
3. 一次含 schema 变更的部署并解释演化，可用历史实例。
4. 生产发布与回退。
5. 模块 A 通过网络调用模块 B，展示状态写回。

截图不能替代。阶段时间由组内安排，但节点不可省略。任务书未给最终截止、展示时长、模板、细分分数和附加项加分，不自行补造。

## Agent 附加项

R-AGENT-01：完成基础系统后，用自然语言覆盖三模块代表操作：M1 查询/预约/历史、M2 申请/状态/撤销、M3 报修/状态/取消等。DSH 插件为建议路线（第 3～4 页）。

R-AGENT-02：调用模块公开接口，不直接访问其他模块数据库，不重写业务逻辑；参数不明确时追问。若完成本项，展示会话驱动业务操作，并将安装、配置、调用纳入交付。项目已选择覆盖此附加项，尚未开发。
