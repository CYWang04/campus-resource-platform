# PJ 任务书分析：校园资源服务平台

> 阅读日期：2026-10-09  
> 主要依据：[Pj-任务书.pdf](Pj-任务书.pdf)，文件标注日期 2026-10-08，共 6 页，已逐页提取文本并核对页面图像。  
> 本文将任务书明文要求、分析判断和实施建议分别标明。本文没有代表小组确定分工、架构或业务规则。

## 1. 项目要交付什么

本学期 PJ 是一套校园资源服务平台，围绕自习座位预约，扩展整教室申请与物业维修。每个项目组独立完成一套完整系统，使用 AI 编程助手开发，并能说明人如何规划任务、约束 AI、验收变更和完成发布。

任务书重视经过思考和规划的开发过程，但仍要求完成业务功能、跨模块集成和交付演示。开发过程与功能交付都需要真实证据，不能用过程文档替代尚未实现的功能。（第 1、4～5 页）

### 明文要求与可自行决定的事项

| 类别 | 任务书规定 | 含义 |
| --- | --- | --- |
| 项目组 | 约 6 人，独立交付完整系统 | 项目组是环境与评级单位 |
| 模块组 | 每组至少 3 个模块组，各认领一个模块 | 模块组是开发与分工单位；未规定每个模块组恰好 2 人 |
| 环境 | 本组独占开发、测试、生产环境，组内共享 | 三类环境不自动等于三台物理服务器 |
| 技术与工具 | 技术栈、AI 工具自选；建议企业级方案 | 没有指定前后端语言、框架或要求微服务；不提供初始化代码或脚手架 |
| 需求细化 | M1 参考附件；M2、M3、D 通过与 AI 交互细化 | AI 可以提出方案，最终基线和验收标准需小组确认 |
| 公共层 | 归属自行决定，须有书面决策记录 | 必须说明方案、考虑因素、依据和组内达成一致的过程 |
| 进度 | 不设统一的阶段完成时间，由各组安排 | 仍有启动、两次 Review、期末展示节点；任务书未给出最终提交截止日期 |
| 基础设施 | 尽量脚本化，推荐 Docker | Docker 是建议，自动化部署与可复现交付是明确要求 |
| 附加项 | 自然语言业务 Agent | 在基础要求完成后扩展，不能替代基础交付 |

## 2. 功能范围和需求完整度

### 2.1 M1：自习座位预约

附件给出的规则较具体，应逐条转为带验收条件的需求。（第 5～6 页）

| 功能 | 明文要求 | 建议验收重点 |
| --- | --- | --- |
| 自习室与座位管理 | 管理员登记、注销、维护可用性和开放时间；座位有唯一编号 | 关闭或注销后的搜索、已有预约如何处理，需要另定规则 |
| 角色与权限 | 管理系统配置、角色及权限；可以设定新角色权限 | 普通学生不能使用管理接口，管理员的数据范围可验证 |
| 院系限制 | 院系自习室只向本院系学生开放 | 搜索和实际预约接口都检查资格，防止绕过前端 |
| 时段预约 | 以整点小时为单位，单次最多 4 小时，参数可调 | 非整点、超过时长和座位时段冲突能被拒绝 |
| 签到 | 教室屏幕每日显示动态、与教室关联的编码或二维码；Web 输码，微信扫码 | 验证编码与教室关联；有效期、签到时段和重复签到规则需细化 |
| 预约前提醒 | 开始前 15 分钟推送 | 有真实推送与可核查结果；邮件或微信等渠道可选择 |
| 未签到提醒 | 开始后 10 分钟再次提醒 | 已签到、已取消预约不会误触发 |
| 自动取消与违约 | 开始后 15 分钟仍未签到，取消预约、释放座位、通知并记一次违约 | 重复执行不重复记违约；与签到并发时处理一致 |
| 搜索与历史复用 | 条件搜索，查历史并再次预定该座位 | 再次预约重新检查当前时段、权限和占用情况 |
| 运营管理 | 查看预约情况，支持调整资源管理策略 | 明确展示哪些指标、什么角色可见；复杂预测模型不是明文要求 |
| 插座标记 | 靠近固定或移动导轨插座的座位标记，支持筛选 | 标记可以维护，筛选结果正确 |

学生端可以选择 Web 或微信小程序，任务书没有要求两种客户端都做。提醒要求包含推送，不能直接将仅写通知表或仅控制台打印当作已完成推送。（第 5～6 页；后一句为验收分析）

### 2.2 M2、M3 和 D：需要形成自己的需求基线

| 模块 | 已给定范围 | 小组需要细化的内容 |
| --- | --- | --- |
| M2 整教室预约与审批 | 权限门槛、申请、多级审批、通过与驳回、超时自动撤销 | 申请资格、审批层级和顺序、超时时长、撤销范围、与现有个人预约的冲突策略 |
| M3 物业报修工单 | 故障上报、派单、维修中、超时升级、完工验收与评价 | 角色与职责、状态转换、谁验收、升级时限与对象、重复工单和取消规则 |
| D 公共层 | RBAC 身份权限、空间与座位主数据、通知、操作审计等 | 数据和接口归属、角色作用范围、通知渠道、审计字段及可见范围 |

任务书要求评估 AI 的候选方案，并先有方案再实现。建议给每条需求分配编号，写出角色、前置条件、正常与异常行为、验收标准，再关联任务、实现、测试和发布版本。未完成需求要保留状态和原因，不能直接从清单删除。（第 2～3 页）

## 3. 跨模块集成是最大的设计难点

### 3.1 明文列出的链路

任务书将下列两条链路列为集成示例，要求小组讨论是否需要补充其他集成点；同时明确要求 M1 座位状态记录写入来源。（第 1～2 页）

| 链路 | 业务效果 | 关键边界 |
| --- | --- | --- |
| M3 → M1 | 自习室有“维修中”工单时，全部座位从可预约列表下架；验收通过后恢复 | 下架触发点是维修中，恢复触发点是验收通过，不能把完工自动等同于验收通过 |
| M2 → M1 | 整教室审批通过后，在预约时段内占用全室座位；驳回或超时撤销后回滚 | 占用受时间范围约束；释放不能误删其他占用来源 |
| M1 状态追溯 | 记录来源为 M1 自身预约、M2 审批占用或 M3 报修下架 | 必须能解释状态为什么改变、由哪个业务记录造成 |

建议把这两条链路作为首版集成基线；若小组选择替代方案，应在需求评审中明确，不宜仅凭“示例”二字自行省略。期末至少必须真实演示一条模块间的网络调用与状态写回链路。（第 5 页）

### 3.2 为什么不能只用一个可用状态字段

以下为设计分析：同一座位可能既受维修限制，又被整教室预约占用。若维修验收后直接设置为“可预约”，就可能错误解除仍然有效的整教室占用。反过来，撤销整教室预约也不能让仍在维修的教室重新开放。

建议将影响可用性的来源独立保存，再计算当前时段是否可以预约。最低限度要区分来源类型、来源业务记录、空间或座位范围、有效时段、是否已解除；操作审计还应记录操作者和发生时间。具体表结构由小组决定。

例如：同一教室有两个维修中工单，验收其中一个，只解除这个工单的限制；另一个仍有效时，座位继续下架。个人预约到期、整教室预约结束和维修解除，也都只应处理各自的来源。

### 3.3 建议优先验证的场景

1. 两人并发预约同一座位、同一时段，只能有一人成功。
2. 整教室审批与个人预约并发，不能出现双方都成功且资源冲突。
3. 维修与整教室占用叠加，解除一项不会错误清除另一项。
4. 同一教室多个维修中工单，只验收一项时仍保持限制。
5. 跨模块接口因网络超时而重试，写回不重复占用、释放或发通知。
6. 撤销、恢复等请求乱序到达时，不会重新应用已失效的旧状态。
7. 签到与逾期取消同时执行，不会既签到成功又被错误记违约。
8. 任一座位状态都能追溯到来源、业务记录和对应操作。

这些是建议测试场景，不是任务书逐条列出的额外功能。它们用于检验原有业务规则在并发和跨模块调用下是否成立。

## 4. 工程过程的硬要求及应保存的证据

以下来自第 2～3 页。右列是方便验收的建议产物。

| 任务书要求 | 建议保留的证据 |
| --- | --- |
| 项目约定以机器可读形式固化并版本管理 | 项目级 `AGENTS.md`、需求规格、接口约定及其变更历史 |
| AI 任务有范围、约束、验收标准，先方案再实现 | 任务单中的方案、边界、验收项，及人工确认记录 |

| 提交能对应任务，说明做了什么、为什么 | 需求或任务编号、清晰的提交说明、小范围变更 |
| AI 变更经人工验收后提交 | 人工检查和验证记录，避免不可审查的巨大补丁 |
| 经合并请求评审后合并 | MR 评审、问题修正和测试结果 |
| 代码冲突由人处理，不得由 AI 自行合并 | 人工处理冲突与确认结果的记录；在 Agent 规则中明确这一边界 |
| 测试失败后续阶段不执行，测试不过不能合并 | 构建与测试门禁、被阻止的失败流水线或 MR |
| 跨模块、公共层和 schema 变更须组内评审 | 相关评审意见、接口与数据兼容性决策 |
| 测试环境自动部署，一次覆盖全组模块 | 无需人工审批的测试部署流水线和全组版本对应关系 |
| 生产发布需人工审批，可回滚且知道当前版本 | 审批、发布 tag、运行版本展示、回退记录与版本说明 |
| 迁移版本化，可重复执行，禁手工改库，空库可重放 | 迁移脚本、迁移历史、空库重建的执行结果 |
| 种子数据脚本化、幂等、与业务数据分离 | 种子脚本及重复执行结果 |
| 协调部署与集成测试 | 部署窗口、互斥锁或等效机制及运行记录 |
| 测试确实验证行为 | 故意破坏实现后测试失败，再恢复实现后通过的记录 |

Git 提交历史是任务书指定的主要过程证据，AI 对话记录可以补充，不能替代。这里需要保留有意义的开发轨迹，任务书没有要求模仿 Lab1 分析对象的提交数量。

关于迁移的“可重复执行”，建议由迁移机制记录版本并安全重入，防止重复应用结构变更；不要据此随意重写已经部署的旧迁移。种子脚本则须重复运行不造成重复数据。生产回滚还涉及新旧代码与数据库结构兼容，不能把回退应用版本直接等同于自动恢复所有业务数据。这些属于实现建议，需要小组决策。

不设统一阶段时间不代表可以省略这些节点。任务书没有提供最终截止时间、展示时长、报告模板、PJ 细分评分权重或附件提交方式。（第 4～5 页）

### 5.2 五项必须实际演示的内容

期末展示必须包含实际操作，截图不能代替：（第 5 页）

1. 从全新环境开始，通过流水线完成部署。
2. 提交一次变更，观察自动触发构建与测试。
3. 执行一次含 schema 变更的部署，说明数据如何演化；可以选择历史中的变更。
4. 演示一次生产发布与回退。
5. 演示模块 A 通过网络调用模块 B，并展示状态写回效果。

做了自然语言 Agent 附加项，还须演示一次会话驱动的业务操作。建议从项目开始就准备演示脚本和可复现数据，避免到期末才发现服务器手工配置、跨模块直接查库或迁移不能重放。

## 6. 附加 Agent 的范围

附加项要求用自然语言完成三个模块的主要操作，示例包括查座位与预约、提交和撤销整教室申请、报修与查询或取消工单。（第 3～4 页）

任务书建议将其作为 DeepSeek Harness（DSH）插件接入，并将插件安装、配置和调用纳入流水线。DSH 插件是推荐路线，不应误写成唯一允许的技术方案。

若实施附加项，以下要求不能省略：

- 真正调用各模块公开接口，不能直接操作其他模块数据库或内部实现。
- 不能在 Agent 中再实现一套预约、审批或报修业务逻辑；这样做本项视为未完成。
- 意图不明确时追问，例如预约教室缺少时间和区域，不能自行填入参数并执行。

分析建议：Agent 使用当前用户权限调用业务接口，服务端再次鉴权；写操作保留审计信息，失败时明确说明结果。先交付基础系统和稳定接口，再实现附加项，避免把时间消耗在聊天界面而基础链路尚未打通。任务书没有给出附加项具体加分。

## 7. 工程伦理必须在开发中留下材料

第 3 页明确要求：各组在开发过程中把工程伦理融入各阶段，每位成员在个人课程论文中，结合本人参与的真实工作讨论问题、应对措施和存疑之处。

以下为适合本项目的分析方向，均属于建议，不能在论文中写成小组已经发生的事件。

| 场景 | 需要讨论的问题 | 可以保存的真实证据 |
| --- | --- | --- |
| 院系限制和审批资格 | 谁可以使用哪些资源，规则是否可解释，是否有不合理排除 | 权限需求、方案比较、角色测试和评审记录 |
| 未签到违约 | 网络、通知或签到系统故障时，自动处罚是否合理 | 异常处理决策、测试、缺陷及后续调整；申诉机制需小组决定 |
| 预约与签到数据 | 哪些身份、位置和行为数据确有必要，谁可以访问 | 字段设计、权限检查、审计与保留期限决策 |
| 整教室占用与维修 | 管理操作是否影响已有个人预约，受影响者是否获知 | 冲突处理规则、通知结果和责任分配 |
| AI 辅助开发 | AI 代码如何验证，来源与许可证如何检查，由谁承担验收责任 | 人工评审、错误测试的修正、来源检查和风险记录 |
| 自然语言业务 Agent | 错误理解是否会造成越权或意外操作 | 追问规则、鉴权测试和真实调用审计 |

个人论文可沿着一项本人实际参与的过程问题展开：记录原有做法、发现的问题、调整方案、验证结果以及仍未解决的限制。论文截止日期、格式和是否需要独立伦理章节，在本任务书中仍未明确。

## 8. 建议的启动顺序与架构考虑

以下是实施建议，不是新增的教师要求。

1. 先确定模块组及公共层责任。列出公共层子域，确认接口所有者、评审人和故障处理人，形成决策记录。
2. 细化需求基线，优先讨论 M2、M3 的状态流转及跨模块冲突规则。给每条需求写可检查的验收条件。
3. 约定统一的空间、座位和用户标识，以及接口、权限、错误返回和状态来源格式，再让 AI 分别提出实现方案。
4. 建立仓库规则、MR 门禁、迁移和种子脚本，尽早完成一次测试环境自动部署。
5. 完成一条最小但真实的业务链路。例如 M3 进入维修中，通过接口让 M1 下架；验收后按来源解除限制。与此同时持续开发三个模块，不能把这条链路当作整个项目的最终范围。
6. 补齐主功能与异常场景，做并发、接口重试和叠加限制测试，验证故意破坏实现会触发测试失败。
7. 完成生产审批、版本标记和回滚演示，再评估是否有余力开发附加 Agent。

架构方面，可以考虑单仓管理多个业务模块，共同编排和部署。至少用于演示的跨模块链路必须有真实网络接口，纯进程内函数调用不能满足第 5 页演示要求。是否全部模块独立为服务、公共层如何部署、数据库是否分库，由小组比较开发成本和契约治理成本后决定。

如果采用共享数据库，也应明确各模块写入的数据范围，防止越过公开接口直接修改另一个模块的业务状态；尤其附加 Agent 明确禁止直接访问其他模块数据库。任务书没有要求微服务、消息队列、Kubernetes 或独立数据库，也没有规定必须有第四个公共层模块组。

### 待确认的业务规则

- M2 审批通过时，已有个人预约是保留、拒绝整教室申请，还是取消并通知？谁有权决定？
- M2 的驳回和超时撤销需要回滚什么？待审批阶段是否提前占用资源？
- M3 的维修范围为何覆盖全室，多个工单如何合并影响，正在使用的预约如何处理？
- 多级审批的层级、人员、权限、代理审批及超时起算点是什么？
- 签到编码如何更新与过期，允许何时签到，迟到或系统故障怎样处理？
- 预约的日期范围、取消规则、签到后离座和闭馆边界是什么？任务书未给出这些细节。
- 通知渠道、真实身份接入方式、服务器分配和网络权限有哪些实际限制？

前六项优先由小组提出并评审需求；涉及学校实际规定或影响资源使用公平的问题，再向教师确认。不能把 AI 随手补出的规则当作已经公布的校方政策。

## 9. 与旧版课程要求的差异

根目录 [课程要求.md](课程要求.md)整理自早期课件和照片。结合 2026-10-08 任务书，应注意以下变化或补充；本文没有改写旧文件。

| 旧文件表述 | 新任务书 | 接手时的处理 |
| --- | --- | --- |
| 3～6 人，最多 6 人 | 约 6 人，每组至少 3 个模块组 | 两份表述未完全相同；分组以最新教师通知确认，不自行推断超过 6 人已获许可 |
| 项目模块范围较笼统 | M1、M2、M3、D 的职责具体化 | 以本任务书建立 PJ 需求基线 |

| 流水线、测试和部署要求概括 | 明确测试门禁、生产审批、可回滚、迁移和真实演示 | 按新任务书补齐交付验收条件 |

最先应推进的三件事是：确定公共层归属、建立可验收的需求基线、跑通最小跨模块链路及自动测试部署。这样后续功能扩展、Review 和个人论文都有持续产生的过程材料可用。
